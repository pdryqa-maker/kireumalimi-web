# 아이디·비밀번호 계정 설계 (2026-11-14)

## 왜
지금의 '간편 로그인'은 계정이 아니다. 부를 이름과 내 정보, 주유 기록이 그 브라우저의 localStorage에만 있다. 그래서 휴대폰에서 남긴 기록을 노트북에서 볼 수 없다.

이용자(배재원)의 말: **"기기를 바꿔도 내 정보와 주유 기록이 따라오게."**

처음에는 카카오 로그인으로 설계했다. 그러다 준비할 것(카카오 앱, 키 3개, DB, 환경변수)이 너무 많아 다시 정했다. 이용자의 결정: **"로그인창을 만들고 그 로그인 계정에 따라 다르게"**. 아이디·비밀번호로 가입하는 우리 계정을 만든다.

나중에는 카카오톡 채널로 들어오게 할 계획이다(이용자). 이번 계정은 그 전까지의 시제품이다.

마감은 2026-11-20(11월 미션 데모)이다.

## 목표
- 아이디·비밀번호로 가입하고, 로그인·로그아웃·회원 탈퇴할 수 있다.
- 아이디는 겹치지 않는다. 같은 이름을 쓰는 사람도 계정은 따로다.
- 로그인하면 계정에 저장된 내 정보와 기록이 그 기기에 보인다. 로그인한 동안 바꾼 것은 계정에도 저장된다.
- 처음 로그인할 때 그 브라우저에 있던 내 정보와 기록을 계정으로 옮긴다. 지금 쓰던 사람의 기록을 잃지 않게 한다.
- 로그인하지 않아도 지금처럼 모든 기능을 쓴다(게스트).
- 탈퇴하면 서버 데이터를 바로 지운다.
- 개인정보 처리방침(/privacy)에 새로 생기는 수집·보관을 적는다.
- 이용자(배재원)가 따로 준비할 것은 없다. 팀원은 Vercel에서 저장소 연결과 환경변수 하나만 한다.

## 하지 않는 것
- 비밀번호 찾기·재설정. 이메일·전화번호를 받지 않으므로 방법이 없다.
  - **화면에 이 사실을 안내하지 않는다(이용자 결정).** 나중에 카카오톡 채널로 옮길 것이기 때문이다.
- 아이디 바꾸기, 비밀번호 바꾸기.
- 카카오·구글 등 다른 로그인. 카카오톡으로 알림 보내기.
- 같은 계정을 여러 기기에서 동시에 고칠 때 칸 단위로 합치기. 마지막에 저장한 쪽을 쓴다(아래 '동기화').
- 채팅 대화 내용 저장. 지금도 저장하지 않는다.

## 이렇게 되면 실패다
- 로그인했다가 기록이 사라진다. 처음 로그인할 때 합치다 잃는 경우, 다른 계정 기록과 섞이는 경우가 여기에 든다.
- 같이 쓰는 PC에서 로그아웃했는데 다음 사람이 앞사람의 기록을 본다.
- 비밀번호가 원문으로 어딘가에 남는다(서버, 로그, 브라우저 저장소).
- 비밀번호를 끝없이 넣어 볼 수 있다.
- 탈퇴했는데 서버에 데이터가 남는다.
- 로그인하지 않은 사람이 무언가를 못 쓰게 된다.
- 시크릿이 코드, 커밋, 채팅으로 새어 나간다.

## 제약
- Next.js 16(App Router, `cacheComponents: true`), React 19, TypeScript strict, Tailwind 4.
  - 코드를 쓰기 전에 `node_modules/next/dist/docs/`에서 쿠키와 라우트 핸들러 사용법을 확인한다(AGENTS.md).
- Vercel 프로젝트는 팀원 계정에 있다. 저장소 연결과 환경변수는 팀원이 넣는다. 이용자는 보호된 프리뷰를 열지 못한다.
- main 병합은 곧 운영 배포다. 이용자가 매번 분명히 허락할 때만 병합한다.
- 시크릿은 `.env.local`과 Vercel 환경변수에만 둔다. `.env.example`에는 이름만 적는다.
- 같은 파일을 고치는 다른 작업이 둘 있다(아래 '다른 작업과 맞추기').
- 새 npm 의존성은 넣지 않는다.

## 방법
### 로그인 방식(이용자가 고름: 아이디·비밀번호)
처음에 견준 세 가지는 카카오 직접 구현(처음 고른 것), Auth.js, Better Auth였다. 셋 다 카카오 앱과 키가 필요해 준비가 많았다.

이용자가 방식을 바꿨다.
- 비밀번호는 서버에 되돌릴 수 없는 형태(해시)로만 둔다.
- 로그인 상태는 서명한 세션 쿠키로 둔다.

### 저장소(처음 고른 것 그대로: Upstash Redis)
| 저장소 | 장점 | 단점 |
|---|---|---|
| **Upstash Redis (선택)** | 브라우저에 저장하는 JSON을 그대로 담는다. 스키마가 없고 무료 등급으로 충분하다. Vercel 저장소 탭에서 연결하면 환경변수가 자동으로 들어간다. | 서울 지역이 없어 도쿄(ap-northeast-1)를 쓴다. |
| Neon Postgres | 표로 통계를 뽑기 좋다. | 테이블 설계와 마이그레이션이 더 든다. |
| Supabase | 서울 지역이 있다. | Supabase 로그인·SDK로 바뀌어 손댈 곳이 많다. |

## 정한 것 (이용자와 함께)
- 계정에 저장할 것: 내 정보와 주유 기록.
- 로그아웃하면 그 브라우저에서 내 정보와 기록을 지운다. 계정에는 남고, 다시 로그인하면 돌아온다.
- 로그인하지 않은 사람은 지금처럼 다 쓴다.
- 로그인은 아이디·비밀번호다. 비밀번호 찾기는 없고, 화면에 그 안내도 없다.

## 빌더의 판단으로 정한 것 (이용자 검토 대상)
대화에서 제안했고 반대가 없어 그대로 간다.
- 알림 조건과 예보 켜기 설정도 계정에 올린다.
- 이름만 넣는 '간편 로그인'은 없앤다. 내 정보 입력 화면은 게스트도 쓸 수 있고, 게스트가 저장하면 그 브라우저에만 남는다.
- 처음 로그인할 때 합치는 규칙은 아래와 같다.

이 문서에서 처음 정한 것은 '[빌더 판단]'으로 표시한다.

## 사용자가 보는 것

### 로그인 화면(/login, 게스트)
```
 ( 불꽃 )  로그인
          로그인하면 다른 기기에서도 내 정보와 주유 기록이 그대로 보여요.
 [ 로그인 | 가입하기 ]
 아이디   [            ]
 비밀번호 [            ]
 (가입하기일 때) 비밀번호 확인 [            ]
 [로그인]  또는  [가입하고 로그인]
 ──────────
 로그인하지 않아도 아래 내 정보를 이 브라우저에만 저장해 쓸 수 있어요.
 부를 이름 / 내 위치 / 내 차 …   (지금 입력 화면 그대로)
 [이 정보로 시작하기]
 개인정보 처리방침
```
- 입력란에는 `autocomplete="username"`, `"current-password"`(로그인), `"new-password"`(가입)를 단다. 브라우저 비밀번호 관리자가 저장해 주도록 하려는 것이다.
- 아이디 규칙 [빌더 판단]: 영문 소문자와 숫자 4~20자. 대문자로 넣으면 소문자로 바꾼다.
- 비밀번호 규칙 [빌더 판단]: 8~64자. 글자 종류는 따지지 않는다.
- 오류 문구 [빌더 판단]
  - "아이디는 영문과 숫자 4~20자로 만들어 주세요."
  - "비밀번호는 8자 이상으로 만들어 주세요."
  - "비밀번호 확인이 달라요."
  - "이미 쓰는 아이디예요."
  - "아이디나 비밀번호가 맞지 않아요."(아이디가 없을 때와 비밀번호가 틀렸을 때 같은 문구)
  - "로그인 시도가 많아요. 10분 뒤 다시 해 주세요."

### 내 정보 화면(/login, 로그인한 사람)
```
 ( 재 )  내 정보
        jaewon99 계정으로 로그인했어요. 어느 기기에서 로그인해도 같은 정보가 보여요.
 부를 이름 / 내 위치 / 내 차 …
 [저장하고 돌아가기]   로그아웃
 ──────────
 회원 탈퇴   ← 작게. 누르면 확인: "계정에 저장된 내 정보와 주유 기록 N건을 지워요. 되돌릴 수 없어요." [탈퇴하기] [취소]
```

### 머리글(AppShell)
- 로그인한 사람: 이름 첫 글자 아바타. 이름이 없으면 아이디 첫 글자. 누르면 내 정보 화면이 열린다.
- 게스트: '로그인' 버튼. 이름을 저장해 둔 게스트도 마찬가지다. [빌더 판단]

### 안내 한 줄
- 처음 로그인하고 합친 뒤: "이 브라우저에 있던 주유 기록 3건을 계정에 합쳤어요." 합칠 것이 없으면 "로그인했어요."
- 가입 직후에도 같은 규칙이다. 게스트 기록이 있으면 합쳤다는 안내가 나온다.
- 로그아웃 뒤: "로그아웃했어요. 이 브라우저에서 내 정보와 기록을 지웠어요(계정에는 남아 있어요)."
- 탈퇴 뒤: "탈퇴했어요. 계정의 내 정보와 기록을 모두 지웠어요."
- 세션만 끝났을 때: "로그인 기간이 끝났어요. 다시 로그인하면 계정과 맞춰요."
- 안내는 화면 위쪽에 한 번 보이고 사라진다. 자리는 빌더가 정한다.

## 동작

### 가입과 로그인
- `POST /api/auth/signup` `{ id, password }`
  1. 아이디·비밀번호 규칙을 검사한다.
  2. 비밀번호를 해시한다.
  3. `HSETNX acct:{id} auth {…}`로 만든다. 이미 있으면 409("이미 쓰는 아이디예요").
  4. 성공하면 `meta`(`createdAt`, `updatedAt`)를 넣고 다섯 칸을 빈 값으로 둔 뒤 세션 쿠키를 준다.
     - 빈 값으로 두는 이유: 탈퇴와 겹친 올리기가 비밀번호 없이 칸만 다시 만들었어도 새로 가입한 사람이 그 기록을 받지 않게 한다. 읽다가 이런 주인 없는 해시를 만나면 지운다.
- `POST /api/auth/login` `{ id, password }`
  1. 실패 횟수가 10분에 5번을 넘었으면 429를 준다.
  2. `auth`를 읽어 비밀번호를 맞춘다(시간 차이로 새지 않는 비교).
  3. 맞으면 실패 횟수를 지우고 세션 쿠키를 준다.
  4. 틀리거나 아이디가 없으면 실패 횟수를 하나 올리고 401을 준다(문구는 같음).
- 비밀번호 해시 [빌더 판단]
  - `node:crypto`의 scrypt를 쓴다. N=2^15, r=8, p=1, 솔트 16바이트, 결과 32바이트.
  - 저장 형식: `auth` 칸에 `{ alg: "scrypt", N, r, p, salt, hash }`(base64).
  - 원문 비밀번호는 로그·응답·브라우저 저장소 어디에도 남기지 않는다.
- 실패 횟수 [빌더 판단]: Redis 키 `fail:{id}`에 INCR, 처음 실패 때 EXPIRE 600초. 아이디가 없어도 센다.
- IP당 호출 제한: 기존 `limitByClient`에 `auth` 한도(10분에 30번)를 더한다.
- 바꾸는 요청(가입, 로그인, 로그아웃, PUT, DELETE)은 `Origin` 머리글이 우리 주소인지 확인한다. [빌더 판단]
- 세션 쿠키 [빌더 판단]
  - 내용: `{ sub: 아이디, ca: 그 계정의 createdAt, iat, exp }`. HMAC-SHA256(`AUTH_SECRET`)로 서명한다.
  - `ca`가 계정의 `createdAt`과 다르면 탈퇴 뒤 같은 아이디로 새로 만든 계정이다. 그 세션으로는 읽기·올리기·탈퇴를 모두 받지 않는다(401 `{ deleted: true }`).
  - 속성: httpOnly, `SameSite=Lax`, https에서는 Secure, `Path=/`.
  - 기간: 30일. 늘려 주지 않는다.

### 서버 저장(Upstash Redis)
- 사람마다 해시 하나를 둔다. 키는 `acct:{아이디}`.
- 칸
  - `auth`: 비밀번호 해시. 브라우저에 절대 보내지 않는다.
  - `meta`: `{ createdAt, updatedAt }`
  - `profile`, `fills`, `ledger`, `alerts`, `watch`: 각각 JSON 글자
- 브라우저 저장소 키와 짝: `kireumalimi.profile` / `.fills` / `.ledger` / `.alerts` / `.watch`.
- 계정에 올리지 않는 것: `kireumalimi.vsArea`, `kireumalimi.areaPrice` 같은 임시 저장값. 다른 작업이 더하는 캐시도 같다.
- 서버는 받은 값을 지금의 검사 함수로 다시 검사해 저장한다. `cleanProfile`, fills 검사, `cleanLedger(…, MAX_SAVED_LEDGER)`, `parseAlerts`, `parseWatch`.
  - 그래서 다른 작업이 Profile에 칸을 더해도 `cleanProfile`만 고치면 계정에도 반영된다.
- 칸 하나의 크기 한도는 64KB. 넘으면 413. 장부 100번이 약 15KB다.
- 보관 기간 [빌더 판단]: 탈퇴할 때까지. 1년 동안 한 번도 쓰지 않으면 자동으로 지운다. 읽거나 쓸 때마다 키 만료를 1년 뒤로 미룬다(EXPIRE).
- Upstash REST API를 `fetch`로 직접 부른다. 쓰는 명령은 HGETALL, HSET, HSETNX, DEL, EXPIRE, INCR 여섯 개다. [빌더 판단]
- 환경변수
  - `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`. Vercel 연동으로 넣으면 `KV_REST_API_URL`, `KV_REST_API_TOKEN`이라 둘 다 읽는다.
  - `AUTH_SECRET`
- 개발 환경(`NODE_ENV !== "production"`)에서 Upstash 값이 없으면 작업 폴더의 `.data/accounts.json`에 저장한다. [빌더 판단]
  - 같은 여섯 명령을 파일로 흉내 낸다.
  - `AUTH_SECRET`이 없으면 `.data/secret`에 무작위 값을 만들어 쓴다.
  - `.data/`는 `.gitignore`에 넣는다.
  - 이용자가 아무것도 준비하지 않아도 내 컴퓨터에서 가입·로그인을 시험할 수 있게 하려는 것이다.
- 운영에서 Upstash 값이나 `AUTH_SECRET`이 없으면 로그인 자리에 "로그인 준비 중이에요"를 보인다. 나머지는 게스트로 그대로 동작한다. 키를 넣기 전에 병합해도 사이트가 깨지지 않게 하려는 것이다.

### 계정 API
- `GET /api/account`
  - 설정 없음: `{ enabled: false, account: null }`
  - 게스트: `{ enabled: true, account: null }`
  - 로그인: `{ enabled: true, account: { id, tag }, data: { profile?, fills?, ledger?, alerts?, watch? } }`
    - `tag`는 `HMAC(AUTH_SECRET, 아이디 + ":" + meta.createdAt)`의 앞 16자다. 같은 계정인지 구분하는 데 쓴다.
    - createdAt을 섞는 이유: 탈퇴한 아이디를 누군가 다시 가입하면 새 계정으로 친다. 그래서 탈퇴 전에 로그인해 둔 다른 기기의 옛 사본이 새 계정에 올라가지 않는다.
  - 세션은 맞는데 키가 없으면(다른 기기에서 탈퇴, 1년 자동 삭제) 401 `{ deleted: true }`를 주고 세션 쿠키를 지운다.
  - Redis가 응답하지 않으면 503을 준다. 브라우저는 이때 아무것도 지우지 않는다.
- `PUT /api/account` `{ tag, data: { profile?: …, … } }`
  - 보낸 칸만 검사해 덮어쓴다. `meta.updatedAt`을 갱신한다.
  - `tag`가 지금 계정의 tag와 다르면 409로 거절한다. 다른 탭에 대기 중인 올리기가 그사이 로그아웃·다른 계정 로그인 뒤 새 계정에 들어가지 않게 하려는 것이다.
  - 모르는 칸이면 400. `auth`와 `meta`도 모르는 칸으로 친다.
- `DELETE /api/account`(탈퇴): Redis 키와 `fail:{id}`를 지우고 세션 쿠키를 지운다.
- `POST /api/auth/logout`: 세션 쿠키를 지운다.
- 호출 제한: `account` 한도 10분에 120번. [빌더 판단]

### 동기화(브라우저 ↔ 계정)
화면 코드는 그대로 브라우저 저장소를 읽고 쓴다. 동기화 층이 다섯 저장소의 변경 이벤트(`{키}:change`)를 듣는다.

- **동기화 상태**: 브라우저 키 `kireumalimi.sync`에 `{ tag, dirty: [칸 이름…] }`을 둔다.
  - `tag`: 이 브라우저의 데이터가 어느 계정 것인지.
  - `dirty`: 이 브라우저에서 바꿨지만 아직 계정에 못 올린 칸.
- **쓸 때**: 동기화할 키에 쓰면 그 칸을 dirty에 넣는다. 로그인 상태면 1.5초 모아서 `PUT`한다. 성공하면 dirty에서 뺀다. 실패하면 남겨 두고 다음 쓰기·화면 열기·창 다시 보기 때 다시 보낸다.
  - 올리는 사이 같은 브라우저의 어느 탭에서든 그 칸이 다시 바뀌었으면(저장소 값이 보낸 값과 다르면) dirty에 남겨 한 번 더 올린다.
  - 창을 떠날 때(숨김)는 미뤄 둔 올리기를 바로, 창을 닫아도 끊기지 않게(`keepalive`) 보낸다.
- **열 때와 창을 다시 볼 때**(1분에 한 번까지): `GET /api/account`.
  - 게스트(`tag` 없음)면 아무것도 안 한다.
  - 세션만 끝났고(30일) `tag`가 남아 있으면 이 브라우저의 사본을 그대로 둔다.
    - '로그인 기간이 끝났어요…' 안내를 한 번 보인다.
    - 그동안 바꾼 것은 dirty로 쌓이고, 같은 계정으로 다시 로그인하면 올린다.
    - 이유: 자기 휴대폰에서 30일 만에 기록이 사라져 보이면 안 된다. 같이 쓰는 PC는 로그아웃 버튼이 지운다.
  - 401(계정이 지워짐)이면 dirty가 있어도 동기화 키와 `tag`를 모두 지운다.
  - 로그인했고 `tag`가 같으면, dirty가 아닌 칸은 계정 값으로 바꾸고 dirty 칸은 올린다.
    - 장부(`ledger`)가 dirty면 통째로 덮지 않고 계정 장부와 날짜로 합쳐 올린다(같은 날은 이 브라우저 것). 오래 못 올린 기기가 다른 기기에서 더한 기록을 지우지 않게 하려는 것이다. 장부에는 지우는 기능이 없어 합쳐도 지운 기록이 되살아나지 않는다.
    - 합치기에서 다섯 칸을 한 번에 올리므로, 같은 tag인 계정에는 다섯 칸이 늘 있다.
  - 로그인했는데 `tag`가 없거나 다르면 '처음 로그인할 때 합치기'로 간다.
- 두 기기에서 같은 칸을 거의 같은 때 고치면 나중에 올린 쪽이 남는다.
- 로그인 상태(계정 있음, 아이디)는 `useAccount()` 훅이 화면에 준다. 첫 그림은 '모름'이고 GET이 끝나면 정해진다. 모를 때는 지금의 아바타 자리 표시를 쓴다.
- 가입·로그인이 끝나면 페이지를 새로 읽지 않고 바로 동기화를 한 번 한다.

### 처음 로그인할 때 합치기
`tag`가 없거나 다를 때 한 번 한다.
1. **`tag`가 다른 계정 것이면** 이 브라우저의 동기화 키를 먼저 비우고 2로 간다. 다른 계정의 기록은 섞지 않는다.
2. **`tag`가 없으면**(게스트로 쓰던 브라우저) 이 브라우저 값과 계정 값을 합친다.
   - `profile`: 계정에 '채운' 내 정보가 있으면 계정 것을 쓴다. 없으면 이 브라우저 것을 쓴다.
     - '채운'의 뜻: 부를 이름을 빼고 `GUEST`(기본값)와 다른 칸이 하나라도 있다.
     - 이유: 빈 노트북에서 먼저 로그인하면 계정에는 기본값만 들어간다. 그 뒤 휴대폰(게스트로 차·위치를 넣어 둠)에서 로그인할 때 그 기본값이 휴대폰 정보를 덮으면 안 된다.
     - 이름은 계정 이름 → 이 브라우저 이름 순으로 고른다.
   - `ledger`: 날짜로 합친다. 같은 날이 양쪽에 있으면 계정 것을 쓴다. 최근 100번까지(`cleanLedger`).
   - `fills`: 날짜로 합친다. 같은 날은 계정 것을 쓴다. 최근 5번까지(`MAX_RECORDS`).
   - `alerts`: 합치고 같은 조건(유종·지역·금액)은 하나만 둔다. 최대 5개, 최근 것부터 남긴다.
   - `watch`: 계정에 켜 둔 것이 하나라도 있으면 계정 것을 쓴다. 다 꺼져 있으면 이 브라우저 것을 쓴다.
3. 합친 값을 브라우저에 쓰고 다섯 칸을 한 번에 `PUT`한다. 성공하면 `tag`를 저장하고 dirty를 비운다.
   - 실패하면 `tag`를 저장하고 다섯 칸 모두 dirty로 둔다. 그래서 로그아웃이 '아직 못 올린 기록'을 묻고, 다음에 열 때나 올릴 때 다시 보낸다. 합치기는 여러 번 해도 결과가 같게 만든다.
4. 안내 한 줄에 이 브라우저에서 계정으로 새로 들어간 주유 기록 수를 보인다.

합치기는 순수 함수로 따로 둔다(`mergeAccount(local, remote) → { merged, addedFills }`).

### 로그아웃
1. 아직 못 올린 dirty가 있으면 먼저 올린다. 세션 쿠키가 있어야 올릴 수 있으므로 쿠키를 지우기 전에 한다.
   - 올리지 못하면 바로 지우지 않고 묻는다: "아직 계정에 못 올린 기록이 있어요. 지금 로그아웃하면 이 기록은 사라져요." [다시 시도] [그래도 로그아웃]. [빌더 판단]
2. `POST /api/auth/logout`로 세션 쿠키를 지운다.
3. 브라우저에서 동기화 키 다섯 개와 `kireumalimi.sync`를 지우고, 첫 화면으로 가서 안내를 보인다.

카카오와 달리 다음 사람이 비밀번호 없이 들어올 수 없으므로 따로 할 일은 없다.

### 회원 탈퇴
1. 내 정보 화면의 '회원 탈퇴' → 확인 창 → `DELETE /api/account`. 미뤄 둔 올리기는 버리고, 이미 보낸 올리기가 끝난 뒤 보낸다(지운 뒤 도착한 올리기가 칸을 다시 만들지 않게).
2. 성공하면 브라우저의 동기화 키와 `kireumalimi.sync`를 지우고 첫 화면으로 가서 안내를 보인다.
3. 로그인해 둔 다른 기기의 사본은 그 기기에서 다음에 열 때 지운다. 그때 `GET`이 401을 준다.
4. '이 브라우저의 내 정보 지우기'(게스트, 로그인 기간이 끝난 사람)는 이 브라우저에서만 지운다. 계정에 올릴 바뀜으로 치지 않아, 다시 로그인하면 계정의 내 정보를 받는다.

### 챗봇과 다른 화면
- 챗봇은 지금처럼 브라우저의 내 정보를 보낸다(`signedIn(profile)` = 부를 이름이 있음). 계정이 생겨도 이 규칙은 그대로다. 서버는 채팅 때 DB를 읽지 않는다.
- `signedIn`이라는 이름은 이제 '내 정보를 저장함'을 뜻한다. 이름을 바꾸면 다른 작업과 겹치므로 그대로 두고 주석만 고친다. [빌더 판단]
- 내 정보 화면의 지금 '로그아웃' 버튼(게스트가 저장한 이름 지우기)은 게스트에게는 '이 브라우저의 내 정보 지우기'로 이름을 바꾼다. 하는 일은 같다. [빌더 판단]

## 팀원이 할 일 (내가 대신 하지 않는다)
